# v1.0.0-rc.5 — fix issue #1 (gradient backgrounds never rendered)

**Date:** 2026-05-26
**Type:** Fix
**Closes:** [#1](https://github.com/myind-ai/myindai-screenshot-mcp/issues/1)

## Summary

Critical render bug: every `render_screenshot` call with a `background_preset` or `background` argument produced a white canvas regardless of the chosen gradient. Root cause was a field-name mismatch between the server's decision builder and the frontend's reader. Fix lives entirely in the frontend via a normalisation layer that accepts every server-side variant — no server-tool changes needed, so every downstream tool that builds a decision object (`render_screenshot`, `generate_screenshot`, the deferred set/variant tools, future contributors) benefits automatically.

While fixing the reported bug I also noticed a second related defect: the dark/light text-colour selection compared `decision.mode === "dark"`, but the server sets `mode` to `"2d"` or `"3d"`. The `_isDark` text path was never taken. Fixed in the same normalisation layer.

## The bug (verbatim from issue #1)

> The server sets `backgroundPreset` in the decision object (`dist/tools/render.js:180`), but the frontend template reads `decision.background` (`frontend/app.js:138`). These are different keys, so gradient backgrounds **never render** — the output is always white.

## The fix

`mcp/frontend/app.js` grows a small `normalizeDecision(raw, defaults)` helper that runs once per render before any field is consumed. It accepts three legal background shapes:

1. `decision.background = "<presetName>"` — original frontend contract.
2. `decision.backgroundPreset = "<presetName>"` — what `render_screenshot` sends today.
3. `decision.background = { type, gradient | solid | image, … }` — rich object (also passed through verbatim from the tool's `input.background`).

Plus the same generality for text colour: `decision.textColor` ("light"/"dark") is honoured first, then legacy `decision.text_color`, then `decision.mode` only if it happens to be exactly "light" or "dark".

The normaliser tags the decision with `_bgPreset`, `_bgObject`, `_bgKind`, and `_isDark`, and the render path consumes those instead of the raw fields. Adding a new alias in the future = one line in `normalizeDecision`.

Case-insensitive preset lookup is included for free — `"Ocean"`, `"ocean"`, and `"OCEAN"` all resolve.

## Regression test

New `mcp/scripts/issue-1-smoke.ts` renders the three legal input shapes and asserts the top-left pixel is not white. Runs without an LLM (`render` direct, not `generate_screenshot`):

```
1. (a) input.background_preset path (what render_screenshot sends)
   top-left RGB = (88, 42, 215)  ✅ coloured  → violet preset
2. (b) legacy decision.background = preset name (string)
   top-left RGB = (0, 177, 255)  ✅ coloured  → ocean preset
3. (c) rich background object — gradient
   top-left RGB = (248, 114, 28) ✅ coloured  → sunset gradient object
✅ all 3 cases rendered a non-white background — issue #1 fix holds.
```

Sample outputs at `/tmp/issue1-case-{1,2,3}.png` for visual inspection. Before the fix, all three pixels read (255, 255, 255).

## Affected callers

Every tool that builds a render decision benefits — but the only tool wired to the renderer in rc.5 is `render_screenshot`. The fix is forward-compatible for:

- `generate_screenshot` (rc.x) — already builds `decision.backgroundPreset` via the AI layer
- `render_aso_set`, `render_ab_variants`, `render_multi_size`, `render_play_store_set`, `render_localized_set` (rc.x) — all share the same decision-builder pattern
- Hand-rolled tool calls from external clients
